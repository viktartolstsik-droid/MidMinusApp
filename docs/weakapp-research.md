# Исследование WeakApp

**Репозиторий:** [nantonov/WeakApp](https://github.com/nantonov/WeakApp), ветка `main`  
**Дата:** 2026-11-03  
**Зачем:** WeakApp — внешний поставщик показаний для MidMinusApp. Нужно зафиксировать, какие HTTP-интерфейсы у него есть и что именно возвращает `GET /meters`.

Это отчёт о наблюдении. Решения по маппингу в наши контракты и правки SDD сюда не входят.

## Как смотрели

В репозитории нет исходников. Есть `README.md`, `Dockerfile`, workflow сборки образа и каталог `publish/` с уже собранным приложением.

Контракт ниже снят декомпиляцией `publish/WeakAppApi.dll` (сборка `WeakAppApi` 1.0.0, TFM из deps: `.NETCoreApp,Version=v9.0`). Рядом лежит PDB; в пути сборки указано `WeakAppApi/obj/Release/net9.0`. Живой `curl` по запущенному контейнеру не делался: образ в реестр не публикуется, workflow только выполняет `docker build`.

README перечисляет те же четыре пути и заголовок `X-Api-Key: supersecret`. Декомпиляция добавляет ещё один путь и всё поведение `/meters`, которого в README нет.

## Как это запускается

`Dockerfile`:

- базовый образ `mcr.microsoft.com/dotnet/aspnet:9.0`;
- копируется `./publish/`;
- `ASPNETCORE_URLS=http://+:8080`, `EXPOSE 8080`;
- точка входа `dotnet WeakAppApi.dll`.

`appsettings.json` задаёт только уровни логов и `AllowedHosts: *`. Отдельной конфигурации ключа, лимитов и портов нет: всё зашито в код.

В `Program` поднимаются контроллеры и OpenAPI. `MapOpenApi()` вызывается только если окружение Development. Dockerfile `ASPNETCORE_ENVIRONMENT` не ставит, так что у контейнера из этого файла эндпоинта OpenAPI нет.

Там же зарегистрирован шаблонный minimal API, к показаниям не относящийся.

## Эндпоинты

| Метод и путь | Авторизация | Кто это в коде | Успешный ответ |
|---|---|---|---|
| `GET /meters` | заголовок `X-Api-Key` | `MetersController.Get`, маршрут `[Route("[controller]")]` | JSON-массив объектов счётчиков |
| `GET /health` | нет | `HealthController` | JSON-строка `"OK"` |
| `GET /healthz` | нет | `HealthController` | `"OK"` |
| `GET /.well-known/health` | нет | `HealthController` | `"OK"` |
| `GET /weatherforecast` | нет | minimal API в `Program` | 5 объектов прогноза погоды, шаблон ASP.NET |

Маршрут контроллера без учёта регистра, то есть `/Meters` и `/meters` — один и тот же GET. Других HTTP-методов на этих путях нет.

Ключ сравнивается как есть: заголовок `X-Api-Key` должен быть равен строке `supersecret`. Иначе **401** и текст `Invalid or missing API key`. Health-ручки ключ не проверяют.

`Ok("OK")` сериализуется форматтером ASP.NET как JSON-строка, не как объект.

## Успешный `GET /meters`

Тело — JSON-массив. Имена свойств в camelCase: так настроен System.Text.Json в ASP.NET Core по умолчанию. Класс элемента — `MeterData`: `Type`, `Name`, `Payload`.

```json
[
  {
    "type": "energy",
    "name": "Kitchen",
    "payload": { "energy": 482.13 }
  },
  {
    "type": "air_quality",
    "name": "Kitchen",
    "payload": { "co2": 640, "pm25": 12, "humidity": 41 }
  },
  {
    "type": "motion",
    "name": "Kitchen",
    "payload": { "motionDetected": true }
  }
]
```

Справочники зашиты в генераторе:

| Поле | Значения |
|---|---|
| `name` | `Kitchen`, `Living Room`, `Bedroom`, `Garage`, `Office`, `Corridor` |
| `type` | `energy`, `air_quality`, `motion` |

На каждую пару `name` × `type` создаётся один элемент, затем список перемешивается. Полный снимок — **18 объектов**. Порядка элементов нет: каждый снимок тасуется заново.

Поля `payload` зависят от `type`. Единиц измерения, id и метки времени в объекте нет.

| `type` | Поля `payload` | Как генерируется |
|---|---|---|
| `energy` | `energy` (number) | `Random.NextDouble() * 1000`, округление до 2 знаков. Фактически `[0, 1000)` |
| `air_quality` | `co2`, `pm25`, `humidity` (int) | `co2` — `Next(300, 1000)` → 300…999; `pm25` — `Next(5, 50)` → 5…49; `humidity` — `Next(20, 80)` → 20…79 |
| `motion` | `motionDetected` (bool) | `true`, если `NextDouble() < 0.5` |

Снимок кэшируется в статическом поле процесса. Новый набор генерируется, если кэш пуст или с прошлого обновления прошло больше одной минуты (`DateTime.UtcNow`). Между обновлениями повторные успешные GET возвращают те же числа. Кэш не общий для нескольких процессов и не переживает перезапуск.

Неизвестный `type` в этой версии генератора не появляется: в `switch` есть ветка с пустым объектом, но в массив типов она не попадает.

## Порядок обработки одного GET

`MetersController.Get` делает шаги строго по очереди. Пока шаг не пройден, следующие не выполняются.

1. **Ключ.** Нет заголовка или значение не `supersecret` → 401, тело `Invalid or missing API key`. Лимит при этом не тратится.
2. **Лимит.** Не больше 10 запросов с одного IP за 40 секунд. Иначе 429.
3. **Задержка.** Почти всегда 100–2000 мс. С вероятностью 0.01 — 30–35 секунд (`Random.Next(30000, 35000)`).
4. **Случайная ошибка.** Вероятность `0.2 + NextDouble() * 0.4`, то есть от 0.2 включительно до 0.6 не включая. Код выбирается равновероятно из трёх: 502 `Bad Gateway`, 504 `Gateway Timeout`, 500 `Unknown error`. Кода 503 нет.
5. **Чтение кэша** — см. следующий раздел.

IP берётся из `HttpContext.Connection.RemoteIpAddress`. Если его нет, ключ лимита — строка `unknown`. Словарь лимита статический, на процесс. Записи старше 40 секунд выкидываются. Момент запроса добавляется в журнал **до** проверки порога, поэтому 429 тоже занимает слот. `Retry-After` — целое число секунд, минимум 1: округление вверх от `40 - (now - самый старый запрос в окне)`.

Из одного контейнера-клиента все запросы видны WeakApp как один IP. Бюджет 10/40 с общий на этот клиент, включая ответы 429 и прочие уже авторизованные вызовы. 401 в бюджет не входит: отказ по ключу происходит раньше.

## Успешный HTTP с пустым или битым телом

Это происходит уже после шагов 1–4, внутри чтения кэша. Два независимых броска, по порядку:

1. С вероятностью 0.1 контроллер выставляет `Content-Type: application/json` и статус 200, синхронно пишет в ответ `{"error":"data corrupted"}` и возвращает пустой список. Дальше `return Ok(пустой список)` пытается записать тело ещё раз. Итоговое тело такого ответа нельзя считать хорошо сформированным JSON-массивом.
2. Если первый бросок не сработал, с вероятностью 0.1 метод возвращает пустой список. Клиент получает обычный **200** и `[]`.
3. Иначе — кэшированный массив из 18 элементов и **200**.

Пустой массив и «битое» тело — разные исходы. Оба выглядят как HTTP-успех до разбора тела.

Оценка частот среди запросов, которые дошли до кэша: около 10% битое тело, около 9% честный `[]`, около 81% полный снимок. До кэша ещё отсекаются 401, 429 и случайные 5xx (20–60% тех, кто прошёл лимит и дождался задержки).

## Чего в API нет

- Записи и удаления. Показания только читаются, источник их не «закрывает».
- Стабильного id показания, id датчика отдельным полем, бизнес-времени.
- Единиц измерения.
- Пагинации, фильтров, query-параметров. `GET /meters` без параметров.
- Отдельного описания схемы в репозитории. OpenAPI в контейнере по Dockerfile выключен.

## Наблюдения для будущего маппинга

Не решение, а то, что придётся учесть, когда маппинг будем согласовывать:

- Наружу для сбора данных торчит только `GET /meters`. Три health-пути годятся как проверка, что процесс жив, и ключ им не нужен. `/weatherforecast` к домену не относится.
- `name` — имя комнаты из фиксированного списка, не координата и не адрес.
- `type` на проводе — `energy`, `air_quality`, `motion`. Внутри `air_quality` три разных числа, внутри `motion` — bool, не число.
- Время показания придётся брать самим в момент успешного ответа: в JSON его нет. Пока кэш не обновился, повторные ответы несут те же величины.
- Образ нужно собирать из репозитория WeakApp. Готового тега в workflow нет.
- Клиентский таймаут короче ~35 с будет обрывать редкий, но штатный медленный ответ.
- Интервал опроса около 1–2 с упирается в 429. Десять секунд между опросами — 4 запроса за окно 40 с и оставляет запас, если часть запросов повторяется.
